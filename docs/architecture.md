# Архитектура «Хранителя» v0.1

Документ фиксирует решения, которые нельзя менять «по ходу»: формат файла, примитивы,
границы ответственности модулей. Всё остальное — детали реализации.

## 1. Модель угроз

Что защищаем: мастер-пароль и содержимое хранилища при краже файла, при доступе к диску
после выхода из приложения и при подмене файла злоумышленником.

От чего защищаемся:

| Угроза | Ответ |
|---|---|
| Файл украден, пароль неизвестен | Argon2id с 64 МиБ памяти делает перебор дорогим |
| Файл изменён (подмена заголовка, байта шифротекста) | AEAD + заголовок как AAD: любое изменение даёт отказ |
| Приложение закрыто, ключ остался в памяти | ключ в `Zeroizing`, зануляется при уничтожении `Vault` |
| Пароль утёк в буфер обмена | автоочистка через 30 с, только если в буфере всё ещё наш секрет |
| Отошёл от машины | автоблокировка через 5 минут, ключ уничтожается |
| Слабый мастер-пароль | минимальная длина 8 символов (слабая защита, см. ограничения) |

Чего НЕ защищаем: вредонос на машине с правами пользователя (keylogger, чтение памяти
процесса), компрометацию самого бинарника, атаки по сторонним каналам на уровне ОС,
физический доступ с извлечением памяти. Это вне возможностей приложения.

## 2. Формат файла (v1)

```
смещение  размер  поле
0         8       magic "OPVAULT1"
8         2       version = 1 (LE)
10        1       kdf_id = 1 (Argon2id)
11        4       m_cost, КиБ (LE)
15        4       t_cost (LE)
19        4       p_cost (LE)
23        16      salt
39        24      nonce
63        ...     ciphertext (JSON + тег Poly1305)
```

- Ключ: `Argon2id(password, salt, m=65536, t=3, p=1) -> 32 байта`.
- Шифр: XChaCha20-Poly1305, nonce 24 байта, новый при **каждой** записи файла.
- AAD: весь заголовок (байты 0..63). Поэтому `m_cost` нельзя понизить, а соль и nonce —
  подменить, не сломав тег.
- Полезная нагрузка: JSON `{ schema: 1, items: [...] }`.

Открытый заголовок нужен, чтобы приложение знало параметры KDF до расшифровки.
Он не содержит секретов: соль и nonce публичны по определению.

Запись файла: временный файл в том же каталоге → `sync_all` → атомарное переименование.
Обрыв питания не оставляет наполовину записанное хранилище.

### Сайдкар Windows Hello (необязательный)

```
смещение  размер   поле
0         8        magic "OPHELLO1"
8         2        version = 1 (LE)
10        12       nonce AES-GCM
22        48       wrapped_key (32 байта ключа + 16 байт тега)
70        ...      dpapi_blob (непрозрачен для ядра)
```

- Ключ хранилища шифруется AES-256-GCM случайным 32-байтным ключом обёртки;
  AAD — магия, версия и nonce.
- Ключ обёртки лежит только под DPAPI в области текущего пользователя: на другой
  машине или учётной записи блоб не разворачивается.
- Перед разворачиванием приложение требует подтверждение Windows Hello.
- Сами вызовы Windows — в `apps/vault-win/src/hello_win.rs`; `vault-core` остаётся
  платформенно-независимым и знает только формат сайдкара.
- Смена мастер-пароля удаляет сайдкар: обёртка соответствует прежнему ключу.
  Удаление сайдкара не вредит самому файлу — вход по паролю работает всегда.

## 3. Модель данных

```rust
Item {
  id: Uuid, kind: Login | SecureNote | Card | BankAccount,
  title, username, password, url, notes: String,
  tags: Vec<String>, fields: Vec<Field>,
  created_at: i64, updated_at: i64,
}

Field { label: String, value: String, sensitive: bool }
```

- `password` и `notes` зануляются в `Drop`, чтобы не оставаться в куче после закрытия записи.
- Поиск намеренно не смотрит на пароль: иначе по выдаче можно подтверждать догадки.
- `VaultData.schema` позволит миграции без ломки формата.

## 4. Границы модулей

```
vault-core   криптография, файл, CRUD, поиск, генератор, импорт и экспорт,
             обёртка ключа Hello, TOTP, аудит. Никакого UI и никаких путей к ОС,
             кроме переданного извне.
vault-cli    тонкая обёртка: ввод-вывод и аргументы. Вся логика — в ядре.
vault-win    eframe/egui: экран входа, список, карточка, буфер обмена, автоблокировка,
             справка. Криптографии обёртки не касается: ключи и формат — в vault-core,
             системные вызовы DPAPI и Windows Hello — в hello_win.rs.
```

Такое разделение позволяет позже добавить Android-клиент на том же ядре (через UniFFI/JNI)
и не переписывать формат.

## 5. Интерфейс

- Один экран входа (файл + мастер-пароль) и один основной экран: слева поиск и список,
  справа карточка записи.
- Пароль в карточке скрыт, пока не нажато «Показать».
- Копирование показывает, что произойдёт с буфером, и через 30 секунд очищает его,
  если там всё ещё лежит скопированный секрет.
- Автоблокировка по бездействию: 5 минут без событий ввода.
- F1 в любом месте окна открывает встроенную справку по всем функциям; текст живёт
  в `apps/vault-win/src/help.rs`, поэтому справка не зависит от внешних файлов.
- Ctrl+Alt+P — глобальный автоввод в активное окно (RegisterHotKey на отдельном
  потоке + SendInput с KEYEVENTF_UNICODE); в окна от администратора ввод не проходит.
- Ошибки не различают «неверный пароль» и «файл повреждён» — это одна формулировка.

## 6. Что проверено тестами

1. Создание → добавление → переоткрытие сохраняет данные.
2. Неверный пароль даёт `InvalidPasswordOrCorrupt`.
3. Порча последнего байта шифротекста обнаруживается.
4. Подмена `m_cost` в заголовке обнаруживается (AAD).
5. Смена пароля: старый перестаёт работать, данные читаются новым.
6. Короткий мастер-пароль отклоняется; существующий файл не перезаписывается.
7. Поиск по названию/логину/сайту/заметкам; пароль не находится.
8. Юникод в мастер-пароле (кириллица) работает.
9. Каждая запись использует новый nonce.
10. Генератор: длина, все классы, отсутствие `Il1O0o`, отклонение пустого набора классов.
11. Windows Hello: обёртка открывает хранилище без пароля.
12. Чужой ключ обёртки, порча сайдкара и подмена магии отклоняются.
13. Смена мастер-пароля удаляет сайдкар; вход по новому паролю работает.
14. DPAPI: раунд-трип ключа обёртки на реальном вызове Windows.
15. TOTP: векторы RFC 6238 для SHA1/SHA256/SHA512, разбор `otpauth://`, мусор отклоняется.
16. Аудит: повторы, короткие пароли, давние записи, сроки и просрочка; разбор дат.
17. Экспорт JSON/CSV: круг «экспорт → импорт» возвращает записи и TOTP-секрет.

## 7. Ограничения и следующие шаги

Ограничения v0.5:

- Нет синхронизации, автозаполнения, passkeys и мобильного клиента.
- Windows Hello: только подтверждение присутствия, без TPM-привязки и без проверки
  доступности до включения опции.
- TOTP-секрет лежит в записи как скрытое поле: его можно раскрыть кнопкой «Показать»,
  как любое скрытое поле.
- CSV-экспорт теряет типы записей (документы уходят как логины) — для полной копии
  используйте JSON.
- Мастер-пароль проверяется только по длине; энтропию не оцениваем.
- `m_cost` 64 МиБ — компромисс между стойкостью и временем разблокировки (~0.3 с).
- Нет внешнего аудита; криптографические примитивы взяты из RustCrypto, свои не писались.

Порядок работ дальше:

1. Android-клиент: Kotlin + Compose, ядро через UniFFI, `AutofillService`, `BiometricPrompt`.
2. Автозаполнение на Windows (аналог Quick Access) и глобальные горячие клавиши.
3. Синхронизация: зашифрованные блобы на сервере, ключ выводится только на устройстве.
4. Passkeys и Credential Provider.
5. Внешний аудит перед тем, как отдавать приложение другим людям.
